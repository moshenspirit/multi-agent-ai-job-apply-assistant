# BOSS 采集运行模式深度调研 — "这个项目适合怎么跑"

> **代号：2026H2P | AI 投递助手 2.0**
> 日期：2026-08-26
> 性质：深度调研（L1 本地源码 → L2 GitHub 原项目 → L3 社区实证 → L4 综合建模）
> 调研对象：`eatmoreduck/boss-zhipin-scraper` v2.2.0（MIT，本仓库 `tools/boss-zhipin-scraper/`）
> 核心问题：**什么样的使用时机最适合这个项目**（像空调适合长时间开、风扇适合短时间开那种匹配关系）
> 红线：决策权在用户；"AI 推断"标注的非建议；合规 = 不自动登录/不自动投递/半自动+人工兜底

---

## 〇、结论速览（TL;DR）

**这个项目不是"跑一天"的空调，也不是"开 5 分钟"的风扇——它是"每周上 2-3 次班、每次 30-60 分钟、一次干完一批活"的洗衣机。**

| 运行模式 | 匹配度 | 一句话结论 |
|---|---|---|
| A. 每天早上开、跑一天 | ❌ 不匹配 | 与源码硬上限直接冲突，token 生命周期撑不住，固定挂机 = 规律信号 |
| B. 每天 9-10 点更新一波 | ⚠️ 可行但有害 | 单次量太小不划算，"每天固定时间"是风控规律信号，日频登录保活 = 账号风险 |
| **C. 隔 2-3 天开一次，一次批量** | ✅ **最匹配** | 单次有硬上限正好用"多关键词×多城市×多筛选"凑批量，低频 = 风控打分低 |

**核心依据（一句话版）**：源码作者亲口确认"单次 10 页 × 15 条 = 150 条是**刻意设置的低频限制**"（Issue #66），且建议"换关键词/城市/筛选条件**分多次抓取，用 --merge 合并去重**"——这本身就是作者设计的正确用法 = **方案 C**。

## 一、L1 本地源码证据（第一手）

### 1.1 源码内置的"运行时机"设计

| 源码常量/逻辑 | 数值 | 含义 |
|---|---|---|
| `MAX_PAGES = 10` | 单次最多 10 页 | 单次会话量硬上限（被动捕获后每页 15 条 = **150 条/关键词/城市**）|
| `MAX_API_REQUESTS = 500` | 单次最多 500 次 API | 全局请求预算，登录探测也计入 |
| 翻页间隔 | `random.uniform(12, 22)` 秒 | 人类化节奏，3 页约 1 分钟 |
| 详情页间隔 | `random.uniform(10, 25)` 秒 | 每条详情 10-25s，10 条约 3-5 分钟 |
| 滚动模拟 | 随机次数/距离/停顿 + 偶尔回滚 | 行为拟人 |
| 登录探测 | 3 组关键词/城市轮换 + 退避（3s→15s）| 避免固定探测模式 |
| 风控识别 | code 31/37 + 关键词兜底（"环境存在异常"/"访问频繁"/"滑块"/"验证"）| 触发即停，**不密集重试** |

### 1.2 8/24 实测数据（我们自己的）

- 单次：AI开发·广州·2页 = **30 条列表 + 详情，耗时 17 分 54 秒**
- 换算：列表 2 页约 2-3 分钟（翻页 12-22s），**大头在详情页**（30 条 × ~30s ≈ 15 分钟）
- **关键推论**：一次跑 30-60 分钟拿 100-300 条是舒适区；"跑一天"意味着 token 反复过期 + 挂机时间呈规律性，两头都踩风控。

## 二、L2 GitHub 原项目证据（作者本人立场）

### 2.1 Issue #66（pages 参数）— **作者亲口确认限流设计**

> "单次上限 10 页 × 15 条 = 150 条。**这是 v2.0.0 起刻意设置的低频限制**（老版本曾无上限，出于请求节奏和风控考虑收紧了）。BOSS 对同一查询条件返回的结果本身也有限。想积累更多数据，**建议换关键词、城市或筛选条件（薪资/经验/行业等）分多次抓取，再用 --merge 按 job_id 合并去重**，就能攒出不重复的大数据集。页数越深越容易触发风控，不建议调得太高。"

→ **这就是作者设计的使用方式 = 方案 C**（多批次凑量 + 合并去重），不是方案 A/B。

### 2.2 Issue #30（CDP 检测 + code 37）— 代理出口 IP 是变量

- 安全 JS 反编译发现：CDP 端口扫描（9222/9223/9229）+ navigator.webdriver + Canvas/WebGL 指纹
- **关键实证**：另一用户遇到持续 code 37，**关闭 Clash（科学上网代理）后恢复正常**——作者确认"code 37 至少在部分场景下与**代理出口 IP 或网络风控**有关"
- 该用户复现细节：**`--setup-chrome` 时开代理 → 之后抓取大概率失败；setup 时关代理 → 之后抓取正常**；且"第一次成功后续失败，不太稳定，有点玄学"
- **推论**：宽带 IP 被标记（我们 8/20 的坑）+ 代理/VPN 出口 IP 不可靠 → **IP 纯净度是运行时机之外的另一个关键变量**

### 2.3 Issue #33（code 37 误判）— 风控 = 临时状态，不是永久

- 作者修 bug：code 37 = 风控/限流响应（RESTRICTED），**不是未登录**
- 已登录用户被风控时 → 停止重试，提示"请先完成验证或稍后再试"
- **推论**：风控有"冷却"概念——触发了就停手等一段时间，**印证"隔几天跑"而非"触发了立刻重试"**

### 2.4 Issue #50（最新发布的岗位）— **数据新鲜度的硬限制**

> "BOSS 网页版搜索页**没有『最新发布』的排序入口**；列表接口返回里**没有任何发布时间字段**；试过 URL 带 sortType 参数，页面不会转发给接口，无效。『搜出来一直是重复岗位』可以用 **--merge 增量去重**解决。"

→ **致命事实**：即使每天跑，也**无法**保证拿到"最新发布"的岗位（没有时间字段可排序/过滤）。每天更新的收益 = 只是"多捞到一些新岗位"，但无法精确增量 → **削弱了方案 B 的核心卖点（数据新鲜度）**

### 2.5 Issue #45（Streamlit + SQLite 断点续跑）— 社区对"收集池"的诉求

- 社区提议：SQLite 任务状态机、单 worker 租约、**暂停/继续**、登录失效恢复、逐条落库
- 这不改 CDP 核心、不换采集方式，只加"持久任务 + 断点续跑"层
- → **这就是你说的"收集池 Agent"形态的社区先行案例**（收集 Agent 独立工作 + 任务状态可恢复）

### 2.6 Issue #67（Chrome 151 后台 Target）— 环境兼容性风险

- Chrome 151 + Linux/Xvfb 后台 Target 无法捕获响应 → 需 `--foreground-capture` 开关
- **推论**：Chrome 版本升级可能破坏采集链路 → 长时间挂机（跨 Chrome 版本周期）维护成本高

### 2.7 AGENTS.md 合规红线（作者硬规则）

> "只做被动捕获（Network 域旁听页面自身请求）和请求节奏控制。**禁止**主动伪装类手段：指纹伪造、验证码绕过、**代理池轮换**。遇到 `_security_check` 验证页时提示用户人工处理，不自动绕过。"

→ **代理池轮换被作者明令禁止** → 我们 8/20 调研报告里的 L0/L6/L7 路线（逆向 token/云浏览器/打码）全部出局，**唯一可持续 = 低频 + 真实浏览器 + 干净 IP**。

### 2.8 README / V2EX 作者原话

> "仅供交流，个人使用无问题，**爬取频率慢，大大降低风控频率**"（V2EX 帖）

## 三、L3 社区实证（别人怎么被封的）

### 3.1 封禁阈值实测数据（多源交叉）

| 阈值 | 数据点 | 来源 |
|---|---|---|
| 单 IP 请求频率 | **8 次/分钟**触发限流（严格）～ 20 次/分钟（宽松）| 逆向分析 / CSDN 问答 |
| 匿名连续爬取 | **10 页左右触发验证码**；触发 5-6 次验证 → **IP 封 24 小时** | CSDN 实战博客 |
| 单 IP 日均 | **超过 200 次请求**可能触发临时封禁 | 聚合项目经验 |
| token 复用 | 相同 `__zp_stoken__` 复用 **超 3 次失效** | 逆向分析 |
| 固定间隔 | 恒定 1.0s 间隔存活率 67%；**1.2-2.5s 随机间隔存活率 92%+** | CSDN 实测 300 次 |
| 频繁重登 | 频繁重新登录 → **账号临时封禁约 1 小时** | CSDN 实战博客 |
| 投递量 | 24h 内超 200 次投递 → **设备指纹永久灰名单** | 逆向分析 |
| 页码深度 | 最多访问前 **15 页**，超出易触发风控 | 爱企查知识库 |

### 3.2 同类工具的处理（AIHawk 限速设计 — DeepWiki 源码级）

| AIHawk 机制 | 数值 | 对照 |
|---|---|---|
| 每页最小等待 | **5 分钟**（MINIMUM_WAIT_TIME_IN_SECONDS=300）| 比本工具 12-22s 保守 10 倍+ |
| 周期性睡眠 | 每 5 页随机 **5-34 秒** | 随机抖动 |
| 长周期睡眠 | collection 模式每 5 页随机 **50-90 秒** | 拉开节奏 |

→ AIHawk 是全自动投递工具（更激进场景），其限速比 boss-zhipin-scraper 严一个数量级 → **印证：BOSS 生态里"慢"是共识，"每天大量跑"没有先例**

### 3.3 BOSS 官方风控力度（2025 安全治理报告）

- **80% 违规账号由 AI 风控主动拦截**；全年封禁数万个违规账号
- AI 语义识别 + 行为建模（"批量索取简历""相似话术反复出现"等模式）
- → 平台在持续加码，**风控只会越来越强** → 长期稳定性必须靠"低调"（低频+拟人），不是靠"技术对抗"

## 四、L4 综合建模 — 三方案对比矩阵

| 维度 | A. 每天开跑一天 | B. 每天 9-10 点 | C. 隔 2-3 天批量 |
|---|---|---|---|
| **风控风险** | 🔴 极高 | 🟡 中高 | 🟢 低 |
| 理由 | ① 单次量远超源码上限（150 条/关键词）；② `__zp_stoken__` 15-60 分钟过期，跑一天 = 反复触发刷新；③ 长时间挂机 = 请求时序规律信号；④ 日均 200 次阈值轻松突破 | ① "每天固定时间" = 风控打分项（请求时序规律性）；② 每天启动登录保活，频繁重登 = 账号临时封 1 小时 | ① 低频 = 时序规律性弱；② 单次控制在舒适区（30-60 分钟）；③ 触发风控后隔几天自然冷却 |
| **数据新鲜度** | 🟡 高但无意义 | 🟡 高但无意义 | 🟢 足够 |
| 理由 | **BOSS 无发布时间字段**（Issue #50）→ 每天跑也拿不到"最新发布"排序，只能靠 --merge 看新增 | 同左；每天增量收益极小 | 2-3 天一次，新岗位覆盖足够；--merge 增量去重照样拿新增 |
| **维护成本** | 🔴 极高 | 🟡 中 | 🟢 低 |
| 理由 | 登录态保活 + token 刷新 + 风控触发的恢复流程，全是日常运维 | 每天手动/定时启动，Chrome 版本更新还可能破坏链路（#67）| 低频启动，一次跑完 --stop-chrome 收尾，登录态保留 |
| **合规** | 🔴 中高 | 🟡 中 | 🟢 低 |
| 理由 | 高频自动化采集 = "对服务造成负担"，突破用户协议禁止条款的司法风险高 | 每天规律性 = 更容易被行为建模识别为自动化 | 个人低频半自动 = 最接近真人使用，司法评价最轻 |
| **与源码设计契合** | ❌ 直接冲突 | ⚠️ 部分冲突 | ✅ 作者推荐用法 |
| 理由 | MAX_PAGES=10 / MAX_API=500 / token 生命周期全被违背 | 单次量太小，为每天跑而每天跑 | Issue #66 原文："换关键词/城市/筛选条件分多次抓取，用 --merge 合并去重" |

**综合评分**：A ❌ / B ⚠️ / **C ✅ 最优**

## 五、推荐运行模式（标注：AI 推断，用户决策）

### 5.1 单次运行模板（"一次上班"的规格）

```
频率：每 2-3 天一次（工作日早上 9-11 点之间，时间可微调避免完全固定）
单次时长：30-60 分钟
单次量：3-5 个关键词 × 2-3 个城市 × 3-5 页 = 300-600 条列表 + 详情子集（top 20-50）
排序：多关键词/城市轮换（不是一次全跑完）
收尾：--stop-chrome 关闭专用 Chrome（保留登录态）
入库：import_boss_json.py → jobs 表（--merge 按 job_id 去重，增量更新）
```

### 5.2 为什么是"2-3 天"（平衡点）

| 频率 | 数据收益 | 风控风险 | 结论 |
|---|---|---|---|
| 每天 | 增量极小（无发布时间字段，--merge 只能去重不能筛新）| 规律信号 + 频繁登录保活 | 不划算 |
| **2-3 天** | 新岗位积累明显；一次 300-600 条够匹配 Agent 消化 | 低频 = 打分低；触发风控有冷却期 | **平衡点** |
| 每周一次 | 数据偏旧 | 最低 | 可作为低频兜底 |

### 5.3 配套措施（让"方案 C"长期成立）

| 维度 | 措施 | 依据 |
|---|---|---|
| **IP** | 宽带 IP 冷却后再用（已被标记）；日常优先手机热点；**禁止代理池轮换**（作者红线 + 合规）；VPN/Clash 运行时不要跑（#30 实证）| L2.2 / AGENTS.md |
| **登录态** | 专用 profile 持久化（已有）；**不频繁重新登录**（封 1 小时风险）；登录态失效 → 手动扫码 | 工具自带 / 3.1 |
| **去重** | 每次 --merge 上次结果（增量）；job_id 为 key；跨关键词/城市也去重 | Issue #50/#66 |
| **降级** | 触发 code 31/37 → 立即停止 → 冷却 1-2 天 → 换 IP 重试；验证码 → 用户手动；**绝不密集重试** | Issue #33 / 源码 |
| **数据落地** | 采集结果进"收集池"（暂存）→ 自检（条数/去重/薪资字段）→ 同步稳定版数据库 → 其他 Agent 只读稳定库 | 用户架构构想 / #45 |

### 5.4 明确不做的（红线）

- ❌ 不逆向 `__zp_stoken__`（合规高危 + 每日换 JS 无限维护）
- ❌ 不代理池轮换 / 不指纹伪造 / 不验证码绕过（作者红线 + 合规）
- ❌ 不自动投递 / 不自动打招呼（平台重点打击 + 用户协议禁止）
- ❌ 不每天高频跑（无收益 + 有风险）

## 六、对 Agent 架构的映射（回应"使用时机决定 Agent 设计"）

**结论：方案 C（隔几天批量）→ 独立收集 Agent + 稳定版数据库分离架构，正是你描述的第二种形态。**

```
┌─ 收集 Agent（独立，隔 2-3 天"上一次班"）─────────────┐
│  启动专用 Chrome CDP（登录态持久）                      │
│  → 多关键词 × 多城市 × 多筛选 轮换批量抓取              │
│  → --merge 增量去重 → 写入【收集池】（暂存，可断点续跑） │
│  → 自检（条数/去重率/薪资字段完整性）                    │
│  → 同步进【稳定版数据库】（其他 Agent 只读这份）          │
│  → --stop-chrome 收尾（登录态保留，隔几天再上班）        │
└─────────────────────────────────────────────────────┘
          ↑ 只此一个 Agent 碰采集链路（风控面最小）
          ↓
┌─ 常驻 Agent 群（读稳定版数据库，不碰采集）──────────────┐
│  匹配 Agent：方向标记 + 条件过滤                         │
│  公司避坑 Agent：DeepSeek 双形态问坑                     │
│  展示 Agent：可投列表卡片 + CSV/MD 导出                  │
│  投递记录：状态流转 + 去重（表已建）                      │
└─────────────────────────────────────────────────────┘
```

**为什么这样分**：
1. **风控面最小化**：只有收集 Agent 碰 BOSS，其他 Agent 完全不碰网络采集 → 风控风险隔离在单个"上班"会话内
2. **断点续跑**：收集池 = Issue #45 的 SQLite 任务状态机形态，中途断电/风控暂停可恢复
3. **数据一致性**：稳定版数据库只在收集 Agent 下班后同步更新 → 匹配/展示 Agent 永远读到一致快照
4. **多 Agent 架构达标**：这正是 2026-08-18 蓝图目标 ③"Multi-Agent 架构成熟项目"的落地形态——**收集 Agent（异步批处理型）与常驻 Agent 群（同步服务型）分离**，各自独立生命周期
