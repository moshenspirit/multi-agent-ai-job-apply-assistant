## 一、用户需求基线（2026-08-19 用户原话拆解）

| # | 需求 | 架构响应 |
|---|---|---|
| 1 | 随时开关的系统，不常驻 | 手动触发为主 + 定时可配（**默认关**） |
| 2 | 每天空闲时投递 | 核心产出 = 可投列表，用户有空打开就投 |
| 3 | Agent 选好目标公司 → 列表给我 | 输出层 = 网页卡片列表 + 导出文件 |
| 4 | BOSS 直聘为主，日后可能拓展 | 采集器策略模式，预留多平台口 |
| 5 | 反爬准备，不能完全自动化 | 半自动采集，反爬处暂停 → 用户手动兜底 |
| 6 | 类型经常变，Agent 听指挥 | 指挥理解 Agent：自然语言指令 → 搜索参数 |
| 7 | 广撒网，匹配要求不高 | 极简匹配：方向标记 + 基础条件过滤 |
| 8 | 单独 Agent 查公司坑 | **公司避坑模块**（双形态，见 3.4） |
| 9 | 最终决策者是用户 | 列表只是建议，用户判读为准 |
| 10 | AI 写简历不需要 | 砍掉简历生成 / 对抗循环 / ATS 评分 |

## 二、整体架构

```
┌─ 触发层 ─────────────────────────────────────────┐
│  [手动开始采集]   [定时自动采集(开关, 默认关)]       │
└───────────────────┬──────────────────────────────┘
                    ▼
┌─ Agent 协作层（用户随时改指令）────────────────────┐
│                                                    │
│  ① 指挥理解 Agent                                 │
│     "搜广州的AI开发岗" → 关键词/城市/方向参数        │
│     （参数动态化，支持用户随时改）                   │
│                                                    │
│  ② 采集 Agent（半自动）                            │
│     Playwright 跑 BOSS 直聘                        │
│     列表 → 翻页 → 详情 → 入库                      │
│     反爬触发（验证码/风控）→ 暂停 → 通知用户手动     │
│                                                    │
│  ③ 匹配 Agent（极简）                              │
│     JD + 简历 → 方向标记(frontend/ai/both/none)     │
│     + 基础条件过滤（城市/薪资）→ 广撒网轻量过筛      │
│                                                    │
│  ④ 公司避坑 Agent（★差异化核心）                   │
│     每个岗位整理"公司信息包"                        │
│     (公司名/规模/行业/岗位摘要/BOSS信息)            │
│     双形态：复制文本自己问 + 内置 DeepSeek 问坑      │
└───────────────────┬──────────────────────────────┘
                    ▼
┌─ 输出层 ─────────────────────────────────────────┐
│  可投列表（网页卡片 + 导出 CSV/MD）                │
│  每张卡：岗位信息 + 方向标记 + 公司信息包          │
│  ★按钮：「复制问坑文本」→ 贴 DeepSeek 判读        │
│  ★内置：「问坑分析」→ DeepSeek 返回隐患提示(参考)  │
│  状态流转：新采集 → 已查看 → 已投递 / 不感兴趣     │
└───────────────────┬──────────────────────────────┘
                    ▼
  用户投递 → 标记"已投递" → 下次采集自动去重
```

## 三、关键设计决定（用户逐项确认）

### 3.1 触发方式
- **手动按钮** ✅ + **定时自动**（APScheduler，**默认关**，用户手动开启 + 设定时间）
- 定时跑完不打扰，用户回来只看列表

### 3.2 输出形态（两种都做，体验后定主次）
- 网页卡片列表（localhost:5173）
- 导出文件（CSV / Markdown）
- 用户原话："不确定，到时实际看看哪个更舒服一点"

### 3.3 匹配（极简）
- 不做复杂评分体系
- 只做：方向标记（frontend/ai/both/none）+ 基础条件过滤（城市/薪资范围）
- 沿用 1.0 的 6 维权重配置（保留，默认轻用）

### 3.4 公司避坑模块（★双形态，用户确认"都要"）
| 形态 | 机制 | 用户流程 |
|---|---|---|
| **被动（复制）** | 列表卡片提供「复制问坑文本」按钮，一键生成"公司+岗位信息包"文本 | 复制 → 贴给 DeepSeek → 看它说的隐患 → 自己判读 |
| **主动（内置）** | 系统内调用 DeepSeek，对岗位生成隐患分析（公司规模/行业/岗位描述异常等信号） | 列表直接显示隐患提示 → **只做参考，用户判读为准** |

**设计原则**：用户是最终决策者。内置分析只标记"需注意"信号，不下"别去"结论；用户保留自己贴 DeepSeek 的习惯。

### 3.5 Agent 化程度
- 三个 Agent（指挥理解 / 采集 / 避坑）+ 匹配服务，用**自研编排类**串（p7 pipeline 模式，Stage 7 先例）
- **不引入** LangGraph / CrewAI / Google ADK（线性流程不需要，避免过度工程）
- 中间产物 JSON 落库（借鉴类型 B Repo 1 模式），任务历史可查

### 3.6 砍掉（用户明确不要）
- ❌ AI 简历生成（用户自己改简历）
- ❌ 对抗循环（Repo 4 模式）
- ❌ ATS 评分卡（Repo 2 模式）

### 3.7 技术栈（沿用 1.0 + 增量）
| 层 | 技术 | 变化 |
|---|---|---|
| 后端 | Flask 3 + SQLAlchemy + SQLite | 不变 |
| 前端 | Vue 3 + Vite + TS + Tailwind + Pinia | 不变 |
| 采集 | Playwright（同步 API） | 不变（1.0 已选型未实现） |
| LLM | **DeepSeek**（OpenAI 兼容端点） | **换**：base_url + model 改配置即可（MiniMax 实测有 `<think>` 块污染 JSON 输出，DeepSeek JSON-mode 100% 稳定） |
| 定时 | APScheduler | **新增** |
| 任务编排 | 自研编排类（p7 pipeline 模式） | **新增** |

### 3.8 反爬策略（1.0 架构文档已设计，沿用）
- 身份伪装 → 行为拟人 → 流量控制（≤100 岗位/次）→ 异常降级（验证码暂停通知用户）
- 红线：不自动登录、不自动投递，最终投递永远用户手动
